LitGraph: a knowledge graph of biology research

Imagine a learning tool where you type in a topic and get back relevant research papers, related concepts, and how they all connect.

LitGraph is a prototype of this tool for molecular biology. It links research papers to the genes, compounds, pathways and diseases that they mention.

My role: sole engineer (I built and designed it with guidance from my company's CEO and CTO). When: July to August 2026 Status: internal tool

Example: searching one rice gene

OsWRKY45 is a well-studied rice gene, known for its role in disease resistance. I type its name, and the dashboard runs this query under the hood:

MATCH (g:Gene {name: 'OsWRKY45'})
MATCH (g)<-[:MENTIONS]-(p:Paper)
OPTIONAL MATCH (g)-[:PARTICIPATES_IN]->(w:Pathway)
OPTIONAL MATCH (g)-[:ASSOCIATED_WITH]->(t:Trait)
OPTIONAL MATCH (p)-[:MENTIONS]->(c:Compound)
RETURN g, p, w, t, c

The result is a searchable graph that shows 69 papers that mention it, the pathway it belongs to, two traits it's linked to, and the compounds those papers discuss.

How the graph is organized

Core

Papers, authors, topics and citations. Common to any field.
PaperCITES →Paper
AuthorAUTHORED →Paper
PaperIN_CATEGORY →Category (arXiv code or MeSH topic)

Biology layer

Genes, compounds, pathways and diseases. A separate package on top of the core.
PaperMENTIONS →Gene · Compound · Disease · Organism
GenePARTICIPATES_IN →Pathway
PathwayPRODUCES →Compound
DiseaseIS_A →Disease

Rice layer

Rice traits, added for the rice corpus.
GeneASSOCIATED_WITH →Trait

Design decisions

A base layer that works for any field

  • The core only has papers, authors and topics, and citations.
  • The graph becomes domain-specific by adding a separate layer with its own node types on top.

One schema, one writer

  • All node and edge types are built from one generic node and edge definition.
  • One graph writer checks and executes every write.
  • A new source only needs to declare its type variant.

Grounded data before LLMs

  • No LLMs or PDF parsing yet. Entities come from PubTator3 and are mapped to standard IDs, while relationships come from curated databases like Gene Ontology and Reactome.
  • Every link can be traced to a source.

Problems that came up (and got fixed)

Slow entity pages

60s1.7sper paper page, in 298K-paper graph

Opening a paper or gene page took up to a minute. I found that ArcadeDB’s query planner scans the whole graph unless the starting node is named and written first. So, I rewrote the queries to ensure this.

Slow first search after DB restart

504s1.3sfirst query after restart

After every restart, the first search waited about 8 minutes while the database rebuilt its vector index. So, I added a service that runs a warm-up query right after each restart, so users don't experience the wait.

Slow bulk writes

~100×faster writes with SQL than with Cypher

Writing data through Cypher was too slow for bulk imports. So, I moved all writes to SQL over HTTP and kept Cypher for reads.

PubMed import cap

9,80051,166rice papers imported

NCBI's API errors out after about 9,500 results per query. So, I split imports into date ranges that stay under the limit.

Empty semantic search

0fixedresults on the big graph

Semantic search returned nothing on the large graph. I found out that deleted index entries were crowding out real results. So, I upgraded the database and that fixed it.

Missing embeddings

108K0papers missing vectors

A GPU server outage silently left 108K papers without embeddings. So, I added retries and a command that finds and fills in any missing embeddings.

Limitation: The graph is only as complete as its entity extraction

46.7%

well-annotated rice genes have no papers linked to them. Manually checking showed that most of them do appear in papers' titles and abstracts, but in short forms like HYR and FZP.

The extractor skips these short symbols because they look like ordinary words, so some genes look less studied than they really are.

Stack

  • Python 3.11, Pydantic, Typer, httpx, uv, pytest
  • ArcadeDB (deployed) and Neo4j, with Cypher for reads and SQL for writes
  • SPECTER2 embeddings (PyTorch) on a GPU server, with a vector index for semantic search
  • PubTator3 for entity extraction; NCBI, Semantic Scholar and arXiv APIs
  • Streamlit dashboard with graph views and a query console; Docker; a cloud VM with cron

What's next

  • Ask questions in plain English. Ground queries with fixed query templates (gene → pathway, author → papers) to avoid hallucinations.
  • Use an LLM to extract semantic relations from full-text PDF, not just mentions.
  • Add more curated sources for pathways and interactions.
